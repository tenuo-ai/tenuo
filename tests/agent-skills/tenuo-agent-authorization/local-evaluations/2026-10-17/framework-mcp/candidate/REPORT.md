# Refund authorization implementation

Authorization result: **development loop**. Tenuo verification runs inside the
original `server.refund_order` effect handler, immediately before the fake journal
write. The handler checks signed authority, trusted issuer, holder proof, expiry,
capability and constrained arguments, then executes the verifier's returned clean
arguments. Strict types reject booleans, strings masquerading as cents, fractions,
and integer/string order substitutions. A separate local ceiling also rejects
broader otherwise-valid warrants. No payment client or payment request exists.

## Scope and trust path

- Issuer: `development.issue_task`, explicitly ephemeral and development-only.
- Holder: separate key generated by `development.demonstrate`; `presentation`
  signs the final request using installed `tenuo_core.sign_meta`.
- Transport: a real subprocess using MCP `stdio_client` and `ClientSession`,
  including `initialize` and `tools/call`; metadata carrier is `_meta.tenuo`.
- Root: `REFUND_TRUSTED_ROOT`, supplied at server startup by the launcher,
  configured as the sole trusted public key. It is never selected by tool
  arguments or request metadata. The verifier process receives no private keys.
- Verifier: `MCPVerifier(Authorizer(trusted_roots=[root]), require_warrant=True)`;
  the handler obtains actual FastMCP request context metadata on both majors.
- Effect: the sole `REFUND_JOURNAL` append in `server.py`. The original module's
  `refund_order` callable remains accessible but enforces checks in its body;
  direct invocation with a configured verifier and no MCP context fails before
  any journal write. There is no retained raw refund helper.
- Task authority and independent local ceiling: `refund_order`, exact string
  order `123`, integer `amount_cents` in **1..50,000 inclusive**. This interprets
  $500 as a **per-call** ceiling, not an aggregate budget. Zero/negative refunds
  are rejected. Task warrants expire in 300 seconds, using server time.
- Ordinary task issuance uses the SDK root issuance defaults for delegation;
  no delegation is needed by the development caller. The delegation regression
  creates a narrower 120-second terminal child with a separate recipient key,
  sends `[parent, child]`, and proves root-only verification. Omitting the parent
  is denied at the receiver. SDK-side widening is rejected; this is explicitly
  issuer-side evidence, not a forged-wider-child receiver test.

This is not a production boundary: the same local launcher controls ephemeral
issuance, public root provisioning, the server subprocess, source files, and the
fake journal path. Production needs an independently owned issuer and server,
protected filesystem/configuration, and appropriately managed keys. Arbitrary
local code with write access can alter these components or write the journal
itself; this implementation does not sandbox the local user/process.

No replay prevention, cumulative budget, idempotency, exactly-once processing,
revocation, approvals, signed receipts, or downstream payment execution evidence
is claimed. Replaying valid authority within its acceptance window may append
again. No observation, optional-warrant, or unknown-argument authorization mode
is enabled. The supported carrier is MCP metadata; argument-carrier/gateway
fallbacks, HTTP/SSE, task/background dispatch, and other effects are outside this
implementation's measured scope. FastMCP may log denial details to local stderr;
production log access/redaction needs review.
